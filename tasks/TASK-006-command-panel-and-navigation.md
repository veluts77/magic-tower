# TASK-006 — Command Panel and Navigation Wiring

## Goal

Подключить модель действий из модуля `domain` (созданную в TASK-005)
к игровому экрану (созданному в TASK-004), чтобы игрок мог видеть
доступные действия, выбирать их и получать результат.

Это первый шаг, в котором игра становится интерактивной.

## Design Context

В TASK-005 мы создали доменную логику:

- состояние игры (текущая комната, посещённые комнаты);
- резолвер доступных действий;
- экзекутор, применяющий действия и возвращающий результат.

В TASK-004 мы создали игровой экран:

- отрисовка комнаты заглушками;
- отображение объектов и маркера персонажа;
- отладочная информация.

Теперь эти две части нужно соединить.

Ключевой архитектурный принцип:

- Домен решает, какие действия доступны и что происходит при выполнении.
- Движок только отображает список действий и передаёт выбор игрока в домен.
- Движок не содержит игровых правил.

Форма отображения действий на этом этапе — простая текстовая панель
или список в нижней/боковой части экрана. Выбор — клавишами.
Это осознанно примитивный вариант. Позже мы будем экспериментировать
с контекстным меню, радиальным меню и другими формами.
Поэтому компонент отображения действий должен быть отделён от экрана
настолько, чтобы его можно было заменить без переписывания экрана.

## Scope

Входит в задачу:

1. Игровой экран запрашивает у домена список доступных действий
   для текущего состояния и отображает их.

2. Каждое действие отображается как текстовая строка
   с номером или клавишей для выбора.
   Например:
    - «1: Осмотреться»
    - «2: Перейти → Зал карт»
    - «3: Перейти → Прихожая»

3. Игрок выбирает действие нажатием клавиши.
   Выбранное действие передаётся в доменный экзекутор.

4. Результат действия отображается на экране как текстовое сообщение.
   Например, при осмотре — описание комнаты.
   При переходе — сообщение о перемещении.
   Сообщение должно быть видно до следующего действия игрока.

5. При успешном переходе экран обновляется:
    - отображается новая комната;
    - объекты новой комнаты рисуются вместо объектов прежней;
    - список доступных действий пересчитывается;
    - отладочная информация обновляется.

6. При попытке выполнить недоступное действие
   состояние не меняется и отображается соответствующее сообщение.

7. Клавиша ESC по-прежнему закрывает приложение.

Не входит в задачу:

- Взаимодействие с конкретными объектами комнаты
  (клик по столу, осмотр книги и т.д.).
  На этом этапе действия применяются к комнате в целом.
- Заклинания, духи, артефакты.
- Контекстное меню, радиальное меню, мышиный ввод.
- Анимация переходов между комнатами.
- Звук.
- Сохранение и загрузка.
- Изменения в модуле `domain`.

## Module Placement

Только модуль `engine`.

Предполагаемые области:

- обновление игрового экрана → `tower.engine.screen`;
- отрисовка панели действий → `tower.engine.render`;
- обработка клавиатурного ввода для выбора действий → `tower.engine.input`.

Перед началом изучи фактическую структуру кода после TASK-004 и TASK-005.
Не предполагай имена существующих классов.

Модуль `domain` не изменяется.
Модуль `desktop` не изменяется.

## Constraints

- Не вносить изменения в модуль `domain`.
- Не добавлять новые внешние зависимости.
- Вся графика — программные заглушки, без файлов изображений.
- Для текста использовать `BitmapFont`, как в TASK-004.
- Компонент отображения списка действий должен получать данные из домена,
  а не формировать их самостоятельно.
  Движок не решает, какие действия доступны.
- Не создавать сложную систему событий или наблюдателей.
  Достаточно прямого вызова: экран запрашивает действия у домена,
  экран передаёт выбор в домен.
- Обработка ввода должна быть простой: нажатие клавиши → выбор действия.
  Не нужна поддержка мыши, геймпада или сложных жестов.
- Сообщение о результате действия не должно быть постоянным элементом
  интерфейса. Достаточно отобразить его до следующего действия.
- Не менять цветовую схему или расположение заглушек из TASK-004
  без необходимости. Новые элементы (панель действий, сообщение)
  добавляются к существующему экрану.

## Acceptance Criteria

1. При запуске приложения отображается комната
   и список доступных действий.
2. В списке есть действие осмотра и действия переходов
   в связанные комнаты.
3. Нажатие клавиши, соответствующей действию, выполняет его.
4. Действие осмотра отображает описание комнаты.
5. Действие перехода меняет отображаемую комнату:
   название, объекты и список действий обновляются.
6. После перехода в новую комнату список действий
   соответствует новой комнате.
7. Повторный переход в уже посещённую комнату работает корректно.
8. При попытке выполнить недоступное действие
   состояние не меняется и показывается сообщение.
9. Отладочная информация обновляется при переходе.
10. ESC закрывает приложение.
11. Модуль `domain` не содержит новых изменений.
12. `./gradlew build` завершается успешно.

## Verification

```bash
./gradlew build
./gradlew desktop:run
```

При запуске:

- видна комната с объектами;
- виден список доступных действий;
- нажатие клавиши выполняет действие;
- осмотр показывает текст;
- переход меняет комнату;
- список действий обновляется.

Проверка, что домен не менялся:

```bash
git diff --name-only domain/
```

Команда должна вернуть пустой результат.
