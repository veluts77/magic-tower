# TASK-005 — Domain State, Action Model and Room Navigation

## Goal

Создать в модуле `domain` минимальное состояние игры, модель доступных
действий и правила перехода между комнатами.

Это фундамент всей интерактивности. Позже заклинания, духи и артефакты
будут подключаться к той же модели действий, не меняя способ отображения
команд в интерфейсе.

## Design Context

Игрок исследует этаж, состоящий из комнат. Переход между комнатами —
первое действие, которое появляется в игре.

Ключевой принцип: действие не должно зависеть от способа выбора.
Панель команд, контекстное меню, горячие клавиши — это будущие варианты UI.
Домен отвечает только на три вопроса:

1. Какие действия доступны сейчас?
2. Что происходит, если выполнить действие?
3. Что изменилось в состоянии мира?

На этом этапе реализуются два вида действий:

- осмотреться — получить описание текущей комнаты;
- перейти — переместиться в связанную соседнюю комнату.

Заклинания пока не реализуются, но модель должна позволять добавить их
позже без переписывания резолвера доступных действий.

Важно: эта задача не меняет внешний вид игры. Визуальное подключение
навигации и команд будет отдельной следующей задачей.

## Scope

Входит в задачу:

1. Минимальное состояние игры в `domain`:
    - текущий этаж;
    - текущая комната;
    - множество посещённых комнат.
      Состояние создаётся на основе ранее загруженных определений этажа.

2. Расширение описания комнаты данными о переходах:
    - каждый переход указывает целевую комнату;
    - при наличии — человекочитаемая подпись или направление.
      Переходы задаются в JSON.
      Направленность переходов явная: автоматическое создание обратного
      перехода не требуется, чтобы позже можно было делать односторонние проходы.

3. Расширение описания комнаты текстовым полем для осмотра.
   Обновить тестовые данные так, чтобы у комнат были описание и переходы.

4. Простая модель действия:
    - идентификатор;
    - тип;
    - цель, если она нужна;
    - отображаемая подпись.
      Без сложных иерархий наследования.

5. Резолвер доступных действий:
    - принимает состояние игры и определения мира;
    - возвращает список действий, доступных в текущей комнате.
      На данном этапе это осмотр и переходы в связанные комнаты.

6. Экзекутор действий:
    - применяет действие к состоянию;
    - возвращает результат: текст сообщения и информацию о том,
      что изменилось в мире;
    - недоступное или неизвестное действие не должно менять состояние.

7. Отметка посещения комнаты:
    - повторный вход не должен создавать дублирующихся записей.

8. Юнит-тесты домена, покрывающие как минимум:
    - корректную инициализацию состояния;
    - состав доступных действий в стартовой комнате;
    - успешный переход в связанную комнату;
    - отказ при переходе в несвязанную комнату;
    - изменение текущей комнаты после успешного перехода;
    - отсутствие дублей при повторном посещении;
    - отсутствие изменений состояния при недоступном действии;
    - получение описания комнаты при осмотре.

Не входит в задачу:

- Изменения рендеринга и ввода в модуле `engine`.
- Панель команд, контекстное меню, любой новый UI.
- Заклинания, духи, артефакты, существа.
- Mastery marks и прогрессия этажа.
- Сохранение и загрузка состояния в файл.
- Бой, урон, поведение монстров.
- Миникарта, fog of war.
- Анимация и звук.

## Module Placement

Только модуль `domain`.

Предполагаемые области ответственности:

- состояние игры → `tower.domain.state`;
- модель действия и результат → `tower.domain.action`;
- резолвер и экзекутор → `tower.domain.logic`;
- определения комнат и переходов → `tower.domain.data`;
- тесты → `domain/src/test`.

Перед началом изучи фактическую структуру проекта после TASK-003 и TASK-004.
Не предполагай имена существующих классов.
Если какое-то состояние уже частично реализовано — расширяй его, а не создавай
параллельную версию.

Модули `engine` и `desktop` в этой задаче не изменяются.

## Constraints

- Main-код `domain` не должен содержать импортов `com.badlogicgames.*` или `Gdx.*`.
- Разрешена ровно одна новая зависимость: JUnit 5 в области `testImplementation`
  модуля `domain`. Никаких других новых зависимостей.
- У `domain` по-прежнему ноль runtime-зависимостей.
- DTO-классы должны оставаться совместимыми с парсером, который используется
  в `engine`: публичные поля или геттеры/сеттеры, конструктор без аргументов.
- Идентификаторы остаются строками; отдельные классы-обёртки для ID не нужны.
- Не вводить событийную шину, ECS, DI-фреймворк или тяжёлые паттерны команд.
- Резолвер не должен быть завязан на конкретные идентификаторы комнат.
  Правила должны работать на данных.
- Экзекутор не должен печатать в консоль, обращаться к файловой системе или UI.
  Результат возвращается значением.
- Состояние не должно быть глобальным mutable singleton.
  Экземпляр состояния передаётся явно.
- Не менять `desktop`. Не менять `engine`.

## Acceptance Criteria

1. В `domain` существует состояние игры, инициализируемое из определений этажа.
2. Описания комнат содержат переходы и текст для осмотра; тестовый JSON обновлён.
3. Резолвер возвращает действие осмотра и действия переходов для текущей комнаты.
4. Экзекутор перехода меняет текущую комнату и отмечает посещение.
5. Недоступный переход не меняет состояние и возвращает понятный результат.
6. Повторное посещение комнаты не создаёт дублей.
7. Юнит-тесты по перечисленным сценариям существуют и проходят.
8. Main-код `domain` не содержит импортов из `com.badlogicgames`.
9. `./gradlew build` завершается успешно.
10. Модули `engine` и `desktop` не изменены.

## Verification

```bash
./gradlew build
./gradlew domain:test
```

Проверка чистоты домена:

```bash
grep -r "com.badlogicgames" domain/src/main/
grep -r "Gdx" domain/src/main/
```

Обе команды должны вернуть пустой результат.

Проверка, что движок и запускатор не изменялись:

```bash
git diff --name-only engine/ desktop/
```

Команда должна вернуть пустой результат.

Запуск GUI в этой задаче не обязателен: поведение проверяется юнит-тестами.
