# TASK-007 — Object Interaction

## Goal

Расширить систему действий возможностью взаимодействия с конкретными
объектами в комнате.

Игрок сможет выбрать объект, увидеть доступные для него действия
и выполнить действие на этом объекте.

## Design Context

В TASK-005 мы создали модель действий, где действие имеет тип и цель.
В TASK-006 мы подключили действия к экрану, но пока только для действий
на уровне комнаты (осмотреться, перейти).

Теперь нужно:

1. Дать игроку возможность выбрать объект в комнате.
2. Для выбранного объекта показать список доступных действий.
3. Выполнить действие на объекте и отобразить результат.

Ключевой принцип:

- Объект может поддерживать разные действия в зависимости от своего типа
  и состояния.
- Домен решает, какие действия доступны для объекта.
- Движок только отображает список и передаёт выбор.

На этом этапе добавляем базовое действие `осмотреть объект`.
Это позволит проверить, что система работает.
Позже добавим специфичные действия (применить заклинание, использовать
артефакт и т.д.).

## Scope

Входит в задачу:

1. Расширить определение объекта комнаты в `domain`:
    - добавить поле `описание` (для действия осмотра);
    - опционально: поле `поддерживаемые действия` или тип объекта
      для определения доступных действий.
      Обновить тестовые данные так, чтобы у объектов были описания.

2. Расширить резолвер действий в `domain`:
    - добавить метод, возвращающий список доступных действий для объекта
      в текущей комнате;
    - на данном этапе возвращать действие `осмотреть объект`;
    - недоступные объекты (если такие будут) не должны возвращать действия.

3. Расширить экзекутор действий в `domain`:
    - поддержать действие `осмотреть объект`;
    - возвращать описание объекта из данных;
    - недоступное действие не должно менять состояние.

4. Расширить состояние игры в `domain`:
    - добавить поле `выбранный объект` (может быть null, если ничего не выбрано);
    - добавить метод для выбора объекта;
    - добавить метод для очистки выбора.

5. В игровом экране `engine`:
    - добавить режимы:
        * режим обзора комнаты (текущий) — показываются действия для комнаты;
        * режим выбора объекта — показываются объекты с номерами для выбора;
        * режим действий с объектом — показываются действия для выбранного объекта.
    - добавить клавиши для переключения режимов (например, Tab или Enter).
    - в режиме выбора объекта:
        * каждый объект отображается с номером;
        * нажатие клавиши с номером выбирает объект;
        * переход в режим действий с объектом.
    - в режиме действий с объектом:
        * показываются действия для выбранного объекта;
        * нажатие клавиши выполняет действие;
        * после выполнения действия — возврат в режим обзора комнаты
          (очистка выбора объекта).
    - в режиме обзора комнаты:
        * можно нажать клавишу для перехода в режим выбора объекта.

6. Отображение результата действия на объекте:
    - при осмотре объекта показывать его описание;
    - сообщение видно до следующего действия.

7. Добавить юнит-тесты в `domain` для:
    - получения действий для объекта;
    - осмотра объекта;
    - выбора и очистки выбора объекта.

Не входит в задачу:

- Специфичные действия (применить заклинание, использовать артефакт,
  призвать духа) — это будущие задачи.
- Взаимодействие с существами.
- Контекстное меню, мышь, сложные жесты.
- Анимация выбора объекта.
- Изменения рендеринга объектов (они остаются заглушками).
- Сохранение и загрузка.

## Module Placement

- Расширение определений объектов → модуль `domain`, пакет `tower.domain.data`.
- Расширение состояния игры → модуль `domain`, пакет `tower.domain.state`.
- Расширение резолвера и экзекутора → модуль `domain`, пакет `tower.domain.logic`.
- Обновление игрового экрана → модуль `engine`, пакет `tower.engine.screen`.
- Обработка ввода для режимов → модуль `engine`, пакет `tower.engine.input`.

Перед началом изучи фактическую структуру кода после TASK-005 и TASK-006.
Не предполагай имена существующих классов.
Расширяй существующую модель действий, а не создавай параллельную.

## Constraints

- Не добавлять новые внешние зависимости.
- У `domain` по-прежнему ноль runtime-зависимостей.
- DTO-классы должны оставаться совместимыми с существующим парсером в `engine`.
- Не создавать сложную систему событий.
- Не менять способ отображения объектов из TASK-004 (они остаются заглушками).
- Добавлять номера к объектам для выбора — можно временно, только в режиме
  выбора.
- Переключение режимов должно быть явным и понятным для игрока.
- После выполнения действия на объекте выбор объекта очищается
  (возврат в режим обзора комнаты).
- Не менять `desktop`.

## Acceptance Criteria

1. В игровом экране есть способ перейти в режим выбора объекта.
2. В режиме выбора объекта каждый объект отображается с номером.
3. Нажатие клавиши с номером выбирает объект и переходит в режим
   действий с объектом.
4. В режиме действий с объектом отображается список доступных действий
   (на данном этапе — осмотреть объект).
5. Нажатие клавиши выполняет действие на объекте.
6. При осмотре объекта отображается его описание.
7. После выполнения действия происходит возврат в режим обзора комнаты.
8. Выбор объекта очищается.
9. В режиме обзора комнаты доступны действия для комнаты (осмотреться,
   переходы).
10. Юнит-тесты для взаимодействия с объектами существуют и проходят.
11. `./gradlew build` завершается успешно.
12. `./gradlew domain:test` завершается успешно.

## Verification

```bash
./gradlew build
./gradlew domain:test
./gradlew desktop:run
```

При запуске:

- видна комната с объектами;
- можно переключиться в режим выбора объекта;
- объекты отображаются с номерами;
- можно выбрать объект;
- видны действия для объекта;
- можно выполнить действие (осмотреть);
- отображается описание объекта;
- происходит возврат в режим обзора комнаты.

Проверка, что модули `desktop` не менялся:

```bash
git diff --name-only desktop/
```

Команда должна вернуть пустой результат.
