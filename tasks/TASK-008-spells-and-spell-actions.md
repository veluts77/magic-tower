# TASK-008 — Spells and Spell Actions

## Goal

Добавить в игру первое заклинание и расширить систему действий
так, чтобы заклинания можно было применять к объектам через тот же
механизм, что и обычные действия.

Это проверка архитектуры: заклинание должно работать через существующую
модель действий, не требуя переписывания.

## Design Context

В TASK-007 мы реализовали взаимодействие с объектами:
выбор объекта → список действий → выполнение действия.

Сейчас доступные действия определяются типом объекта.
Например, все объекты поддерживают действие `осмотреть`.

Теперь нужно расширить это:

- У игрока появляется состояние: список известных заклинаний.
- Заклинания загружаются из JSON-файлов.
- Объекты могут поддерживать определённые заклинания.
- Если у игрока есть заклинание И объект его поддерживает,
  это заклинание появляется в списке доступных действий для объекта.

Пример:
- У игрока есть заклинание `spark` (искра).
- Объект `факел` поддерживает заклинание `spark`.
- Игрок выбирает факел.
- В списке действий появляется `Применить: Искра`.
- Игрок выполняет действие.
- Факел загорается (состояние объекта меняется).

Это демонстрирует, что заклинания — это просто ещё один тип действий,
и система масштабируется.

## Scope

Входит в задачу:

1. Модель заклинания в `domain`:
    - идентификатор (строка);
    - отображаемое имя;
    - описание;
    - тип цели (что можно этим заклинанием воздействовать: объект, комната, существо).
      На данном этапе используем только тип `объект`.

2. Состояние игрока в `domain`:
    - список идентификаторов известных заклинаний;
    - метод добавления заклинания;
    - метод проверки, знает ли игрок заклинание.

3. Загрузка заклинаний из JSON:
    - создать структуру `assets/data/spells/`;
    - создать тестовый JSON с описанием одного заклинания `spark`;
    - расширить `DataLoader` для загрузки заклинаний.

4. Расширение определения объекта в `domain`:
    - добавить поле `поддерживаемые заклинания` (список идентификаторов заклинаний).

5. Расширение состояния комнаты в `domain`:
    - добавить поле для хранения состояния объектов
      (например, `состояние факела: зажжён/погашен`);
    - или использовать флаги комнаты для отметки изменений объектов.

6. Расширение резолвера действий в `domain`:
    - при получении действий для объекта, если у игрока есть заклинание
      и объект его поддерживает, добавить это заклинание в список действий;
    - действие должно иметь тип `применить заклинание` и цель `идентификатор заклинания`.

7. Расширение экзекутора действий в `domain`:
    - поддержать действие `применить заклинание`;
    - при выполнении заклинания `spark` на поддерживающем его объекте
      изменить состояние объекта (например, отметить как `зажжён`);
    - возвращать текстовый результат выполнения заклинания.

8. Инициализация состояния игрока:
    - при старте игры игрок знает одно заклинание `spark`;
    - это можно сделать через код (не через сохранение).

9. Обновить тестовые данные:
    - в тестовой комнате должен быть хотя бы один объект, поддерживающий `spark`;
    - этот объект должен иметь описание для осмотра.

10. Юнит-тесты в `domain` для:
    - загрузки заклинания;
    - добавления заклинания в состояние игрока;
    - проверки, что игрок знает заклинание;
    - получения действий для объекта с поддержкой заклинания;
    - выполнения заклинания на объекте;
    - изменения состояния объекта после выполнения заклинания;
    - отсутствия заклинания в действиях, если игрок его не знает;
    - отсутствия заклинания в действиях, если объект его не поддерживает.

Не входит в задачу:

- Другие заклинания (только `spark` для проверки архитектуры).
- Духи, артефакты, существа.
- Mastery marks и прогрессия этажа.
- Получение заклинания через геймплей (пока даём при старте).
- Сохранение и загрузка состояния игрока.
- Визуальные эффекты заклинания (анимация, частицы).
- Изменения рендеринга (объект может менять цвет или подпись после заклинания,
  но без сложных эффектов).

## Module Placement

- Модель заклинания → модуль `domain`, пакет `tower.domain.data` или `tower.domain.spell`.
- Состояние игрока → модуль `domain`, пакет `tower.domain.state`.
- Расширение резолвера и экзекутора → модуль `domain`, пакет `tower.domain.logic`.
- Загрузка заклинаний → модуль `engine`, пакет `tower.engine.data`.
- Тестовые JSON-файлы → `assets/data/spells/`.
- Инициализация состояния игрока → модуль `engine`, в главном классе или экране.

Не предполагай имена существующих классов.
Расширяй существующую модель, а не создавай параллельную.

## Constraints

- Не добавлять новые внешние зависимости.
- У `domain` по-прежнему ноль runtime-зависимостей.
- DTO-классы должны оставаться совместимыми с существующим парсером в `engine`.
- Заклинание работает через существующую модель действий,
  не требует отдельной системы.
- Не создавать систему маны, кулдаунов или стоимости заклинаний.
- Не менять способ выбора объектов из TASK-007.
- После выполнения заклинания объект должен как-то измениться
  (текстовое описание, флаг состояния, цвет заглушки).
- Не менять `desktop`.

## Acceptance Criteria

1. В `assets/data/spells/` существует JSON-файл с описанием заклинания `spark`.
2. Заклинание загружается при старте игры.
3. Игрок при старте знает заклинание `spark`.
4. В тестовой комнате есть объект, поддерживающий `spark`.
5. При выборе этого объекта в списке действий появляется `Применить: Искра`
   (или аналогичное).
6. Выполнение заклинания на объекте меняет его состояние.
7. После выполнения заклинания отображается сообщение о результате.
8. Если игрок не знает заклинания, оно не появляется в действиях.
9. Если объект не поддерживает заклинание, оно не появляется в действиях.
10. Юнит-тесты для всех сценариев существуют и проходят.
11. `./gradlew build` завершается успешно.
12. `./gradlew domain:test` завершается успешно.

## Verification

```bash
./gradlew build
./gradlew domain:test
./gradlew desktop:run
```

При запуске:

- видна комната с объектами;
- можно выбрать объект, поддерживающий заклинание;
- в списке действий появляется `Применить: Искра`;
- выполнение заклинания меняет объект (например, меняется подпись или цвет);
- отображается сообщение о результате.

Проверка, что модуль `desktop` не менялся:

```bash
git diff --name-only desktop/
```

Команда должна вернуть пустой результат.
