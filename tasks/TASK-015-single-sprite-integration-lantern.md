# TASK-015 — Single Sprite Integration: Magic Lantern

## Goal

Подключить первый реальный спрайт в игру: изображение магического фонаря,
которое пользователь уже создал и сохранил в `assets/images/lantern.png`.

Это небольшой вертикальный срез, чтобы проверить пайплайн интеграции
графики, не переделывая весь рендеринг сразу. Все остальные элементы
по-прежнему остаются программными заглушками.

## Design Context

До сих пор вся графика рисовалась программно:
цветные фигуры для объектов, маркер персонажа, текстовые подписи.

Теперь мы начинаем заменять заглушки на реальные спрайты.
Чтобы не сломать работающую игру, делаем это по одному объекту.

Ключевые принципы:

- Модуль `domain` не знает о файлах, текстурах и путях к ассетам.
- Связь между игровым объектом и изображением живёт в `engine`.
- Если спрайт не загружен, игра не должна падать:
  объект продолжает отображаться заглушкой.
- Существующая механика выбора объектов и действий не меняется.

Временное исключение из `ART_MANIFEST.md`:
использовать существующий файл `assets/images/lantern.png` как есть,
не требуя пути и имени из манифеста. Позже мы сможем привести
именование ассетов к манифесту отдельной задачей.

## Scope

Входит в задачу:

1. Найти в существующих данных объект магического фонаря в комнате
   `map_hall` (Зал карт). Изучить фактический JSON и код после
   предыдущих задач, чтобы определить реальный идентификатор объекта.
   Если объект фонаря не найден, сообщить об этом как о блокере,
   не придумывая новый объект.

2. Добавить в `engine` минимальный механизм загрузки одного изображения:
    - загрузить `assets/images/lantern.png`;
    - учесть, что рабочая директория запуска указывает на `assets`,
      поэтому внутренний путь, скорее всего, будет `images/lantern.png`;
    - корректно освободить ресурс при завершении работы экрана или игры.

3. Создать в `engine` простое сопоставление между игровым объектом
   и спрайтом. На этом этапе достаточно одной записи для фонаря.
   Не нужно делать полноценную data-driven систему спрайтов.

4. При отрисовке комнаты заменять графическую заглушку фонаря
   на загруженный спрайт. Остальные объекты продолжают рисоваться
   заглушками.

5. Спрайт должен вписываться в существующие границы объекта,
   которые сейчас занимает заглушка. Сохранять пропорции изображения.
   Не требовать предварительного ресайза файла пользователем.

6. Для масштабирования пиксель-арта использовать nearest-neighbor
   фильтрацию, чтобы не размывать пиксели.

7. Корректно отображать прозрачность PNG, если она есть в файле.

8. Сохранить существующие подписи, номера объектов и режимы выбора.
   Спрайт заменяет только графическую фигуру, а не весь визуальный
   элемент объекта.

9. Если файл отсутствует или не загружается, объект должен
   отображаться прежней заглушкой, а в лог должно попасть предупреждение.
   Игра не должна падать.

Не входит в задачу:

- Подключение любых других спрайтов.
- Изменение разрешения окна.
- Изменение layout объектов или камеры.
- Переход на TextureAtlas.
- Асинхронная загрузка ассетов.
- Анимация.
- Отдельные спрайты для зажжённого и потушенного фонаря.
- Изменение игровой логики, действий, заклинаний, печатей.
- Изменения в модуле `domain`.
- Изменения в модуле `desktop`.
- Перемещение или переименование файла `assets/images/lantern.png`.

## Module Placement

Только модуль `engine`.

Предполагаемые области:

- загрузка и хранение текстуры → `tower.engine.render`;
- сопоставление объект → спрайт → `tower.engine.render`;
- отрисовка объекта → существующий renderer комнаты;
- освобождение ресурсов → экран или renderer, в зависимости от
  текущей структуры кода.

Перед началом изучи фактическую структуру кода после TASK-004,
TASK-006, TASK-007 и TASK-013. Не предполагай имена классов.
Если механизм загрузки текстур уже существует, используй его,
а не создавай параллельный.

## Constraints

- Не добавлять новые внешние зависимости.
- Не изменять модуль `domain`.
- Не изменять модуль `desktop`.
- Не менять JSON-данные, если это не требуется для поиска объекта.
- Не создавать новые игровые объекты.
- Не использовать сглаживание при масштабировании спрайта.
- Не ронять приложение при отсутствии файла.
- Не делать универсальный фреймворк спрайтов на этом этапе.
  Достаточно минимального решения для одного объекта.
- Не трогать остальные заглушки.

## Acceptance Criteria

1. Файл `assets/images/lantern.png` используется игрой.
2. В комнате `map_hall` объект фонаря отображается спрайтом,
   а не цветной фигурой.
3. Остальные объекты по-прежнему отображаются заглушками.
4. Подписи и номера объектов сохраняются и читаются.
5. Выбор фонаря и действия с ним работают как раньше.
6. Применение заклинания к фонарю по-прежнему работает.
7. Прозрачность PNG отображается корректно, если она есть.
8. Пиксели не размываются при масштабировании.
9. При отсутствии файла игра не падает, объект рисуется заглушкой,
   в лог попадает предупреждение.
10. Ресурсы текстуры освобождаются при завершении работы.
11. Модуль `domain` не изменён.
12. Модуль `desktop` не изменён.
13. `./gradlew build` завершается успешно.
14. `./gradlew domain:test` завершается успешно.

## Verification

```bash
./gradlew build
./gradlew domain:test
./gradlew desktop:run
```

При запуске:

- перейти в Зал карт;
- убедиться, что фонарь отображается изображением;
- убедиться, что остальные объекты остались заглушками;
- выбрать фонарь и выполнить доступные действия;
- убедиться, что механика не сломалась.

Проверка, что домен и запускатор не менялись:

```bash
git diff --name-only domain/ desktop/
```

Команда должна вернуть пустой результат.

Если GUI недоступен, достаточно успешной сборки и тестов,
а в отчёте указать: `GUI not tested`.
